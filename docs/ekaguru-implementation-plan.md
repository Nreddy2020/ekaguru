# EKAGURU implementation plan

Updated 11 September 2026. This is the durable plan for continued implementation, not a claim of global product completeness.

## Verification gate
Define acceptance before each stage; implement, test the appropriate unit and actual integration/UI behavior, inspect and repair failures, then record evidence and limits before proceeding to dependent work. Pending or mocked verification is not live runtime proof. A blocked stage permits only genuinely independent authorized work. Routine user approval is not required.

## Intended outcome
A learner opens their own textbook page in the already approved EKAGURU classroom. Guru teaches that exact page with progressive writing, drawings, spoken explanations, level-appropriate reasoning and checkpoints. The original source remains available, and progress or mastery claims require recorded evidence.

## Architecture decisions
- Preserve the approved library/classroom references in approved-interface-architecture.md.
- Carry book ID, physical page, source hash and learner preferences through extraction, planning, runtime and source highlights.
- Keep model provider credentials on the server. Validate model output and evidence IDs before presenting or persisting it.
- Keep page-practice observations separate from canonical mastery until concept mapping is verified.
- Preserve originals. Never substitute an EVS sample for an unavailable upload.
- Store local PDFs in IndexedDB; distinguish device-local originals from authorized server materials.
- Continue existing Gemini support while implementing the user's requested OpenAI option through the same model boundary.

## Stage completed 11 September 2026 (later): first live Guru lessons
Acceptance defined in advance: (a) a real multimodal lesson for a real scanned page is accepted by the unchanged server validators and plays in the approved classroom; (b) a learner answer is graded live and the checkpoint releases; (c) every failure met on the way is either fixed in code with a test or recorded as a known limit; (d) the provider key lives only in the ignored backend `.env`.

Live results with Gemini (`gemini-2.5-flash`; the newer `gemini-3.8-flash` answered probes but returned 503 high-demand for real lessons):
- EVS Class 5 page 46 at basis depth: accepted after one repair pass, 17 actions covering 14 of 15 vision blocks with the page number explicitly omitted, model review passed, about 117 s. Advanced depth: accepted, 17 actions, about 172 s. Both are stored as corpus artifacts for educator review.
- In the in-app browser the basis lesson played on the approved board and the checkpoint "What kind of things do people usually buy at a market?" blocked Next. A typed learner explanation was graded live: criteria met 2 of 2, confidence 1.0, feedback shown on the board, Next released, progression to action 7 of 17 confirmed. The assessment carried `masteryUpdated:false` with note `bridge-disabled`, and the board now renders that note in plain language.
- Failures found and fixed: 12k output-token cap truncated transcriptions (now 32k, configurable); 90 s deadline aborted deep and developing plans (now 180 s, configurable); free-tier 429 throttling under concurrent generation (bounded retry, at most two waits); plans that skipped a page-number block, omitted rectangle heights, emitted empty notes or empty action text (explicit `omitted` list with reasons, Gemini structured output on planning, grading and page questions, clamped scene geometry, one validator-guided repair pass, notes defined in the prompt); a whole page rejected for one low-confidence region (uncertain regions are now set aside, reviewer-visible, capped at a quarter of blocks); a grading reply rejected for shape (structured output plus a content-free shape diagnostic in the server log). The vision transcription is cached per page image and model so five depths share one vision call.
- With the hardened code, developing (16 actions, about 162 s) and deep (16 actions, about 218 s) were accepted for page 46. Proficient hit the 32k output-token cap on one call, then the 180 s deadline; the default cap was raised to 48k (Gemini 2.5 Flash allows 65,536) and it was accepted on the third attempt with a 300 s deadline (21 actions, about 149 s). All five depths of page 46 are now prepared for educator review. Every attempt, success or failure, is appended to `docs/evaluation/prepare-results.jsonl`.

Depth differentiation observed on the same page: the basis lesson's checkpoints ask recall-level questions ("What kind of things do people usually buy at a market?", rubric of 2 criteria), while the advanced lesson's checkpoints ask "Why are markets important?", "What are the broader benefits of parks?" and "How do banks support the economy?" with 3 criteria each and objectives about economic and social roles. This is the first live evidence that depth can change reasoning demand. It is not yet consistent: the accepted deep lesson's checkpoints ("Why do people go to a market?", "Do you have friends in your neighbourhood?") are no more demanding than the developing lesson's, so the model did not honour the first-principles instruction for deep on this page. That inconsistency is exactly what the educator corpus must measure (pedagogical progression criterion) before any depth is approved; the planner prompt is deliberately left unchanged until the v1 corpus has been scored, so results stay comparable.

Limits: these are engineering acceptance results, not educator judgements; no rubric review has been recorded yet. The free tier throttles concurrent generation, so corpus preparation must run serially. The API key that was pasted in chat had already been revoked by Google as leaked before use; the replacement was entered directly into `.env` and must be rotated if it ever appears in a transcript or log.

## Findings and additions after the first live day (11 September 2026, later)
- Free-tier limit is the real blocker for the corpus: Google's quota for `gemini-2.5-flash` on this project is 20 requests per day (`GenerateRequestsPerDayPerProjectPerModel-FreeTier`). One lesson needs 3 to 4 calls, so the free tier yields at most about five lessons a day per model. The 25-case pilot batch failed every case within 47 seconds each once the quota closed. The model boundary now recognises a per-day quota violation, does not retry it, and returns a distinct message; the corpus script stops the batch on that message instead of burning through the remaining cases. Preparing the 185-case corpus (roughly 600 to 750 calls) requires pay-as-you-go billing on the Google AI Studio project or a paid provider; the code path is otherwise proven.
- Learner attribution for built-in textbooks: a signed-in parent can now choose a learner profile in Guru settings; the session is bound to that learner after ownership verification, sessions are kept separate per learner, private materials still bind only to their own learner, and a mismatching request is refused. This removes the "no-learner" gate for built-in books and closes the "learner selector for shared parent accounts and builtin books" requirement from the architecture review. Covered by runtime and studio tests, and verified in the in-app browser: a disposable parent with two learner profiles opened page 46, chose one learner in Guru settings, and the server created a second session bound to that learner while the unattributed session stayed separate (confirmed in the database).

Evidence at the end of the day: backend 63 of 64 suites, 396 of 399 tests (legacy Socratic contract test only); frontend 28 suites, 132 tests; TypeScript clean on both sides.
