# Load check, 11 September 2026

Tool: autocannon 7, 20 connections, 10 seconds per endpoint, against the local development backend (`nest start --watch`, one process, ts-node, local PostgreSQL in WSL). These are relative numbers for finding bottlenecks, not capacity figures for a production build.

| Endpoint | Before | After | Note |
| --- | --- | --- | --- |
| `GET /health` | 6,219 req/s, p50 2 ms, p99 9 ms | unchanged | framework floor |
| `GET /api/v2/textbooks/evs-class-5/pages/46/evidence` | 53 req/s, p50 373 ms, p99 483 ms, about 2.4 MB per response | 234 req/s, p50 84 ms, p99 112 ms, about 10 KB per response | the scan left the JSON; it is now a separate immutable image |
| `GET …/pages/46/image` | not present | 39 req/s, p50 583 ms, 1.8 MB per response | fetched once per source revision per browser (`Cache-Control: public, max-age=31536000, immutable`, ETag = source hash, 304 on revalidation) |
| `POST …/pages/46/lesson` (cached lesson) | 182 req/s, p50 107 ms, p99 142 ms | unchanged | one artifact read plus rubric stripping |

Findings and what was done:

1. Every evidence read shipped the full page scan as base64 inside the JSON. Page opens on a phone therefore cost 2.4 MB each time. The evidence response now carries an `imageUrl`; built-in scans are served by a public immutable image endpoint and private uploads by a signed, expiring image URL (an `<img>` cannot send a bearer header). The classroom prefers `imageUrl` and keeps inline data URLs only for PDFs stored in the browser.
2. Page evidence (OCR blocks) is persisted per source revision, so a restart or a second replica no longer re-runs Tesseract (2.4 s to 0.7 s for a fresh process, zero OCR calls).
3. Remaining cost in the evidence path: each request still reads the 1.8 MB scan from disk and hashes it to establish the source revision before hitting the in-memory cache. A stat-keyed hash cache would remove most of the 84 ms; not done yet.
4. Not measured: OCR of a first-time upload, lesson generation (model-bound, seconds to minutes and queued), and concurrent Guru sessions writing events. A production build with several replicas and a shared cache is the right setting for capacity numbers.
